# Native linear and positive logarithmic axes

`axes: 'scaled-axes-v1'` is a new, explicit **native line/scatter** profile.
Each axis independently accepts `xScale` / `yScale`: `'linear'` (the default) or
`'log10'`. It is separate from the unchanged `numeric-axes-v1` profile and the
browser/ECharts axis API. The separate [scaled machine provider](plot-provider-scaled.md) exposes this
profile through a new command; existing machine commands remain closed.

```ts
import { figure } from 'plot-ts/svg';

const chart = figure({ width: 600, height: 360, theme: 'sage' })
  .line({
    axes: 'scaled-axes-v1',
    xScale: 'log10',
    yScale: 'log10',
    xDomain: [1, 1000],
    yDomain: [1, 1000000],
    xUnit: 'Hz',
    unit: 'W',
    legend: 'series-names-v1',
    x: [1, 10, 100, 1000],
    series: [{ name: 'Power law', y: [1, 100, 10000, 1000000] }],
  });
const svg = chart.render();
const html = chart.renderHtml();
const frame = chart.renderFrame(150);
```

Changing only X to logarithmic makes a semilog-X chart; changing only Y makes a
semilog-Y chart. A scatter uses the same options with its usual `points` array.
`ScaledAxesProfile`, `NativeAxisScale`, `NativeAxisDomain` and `ScaledAxesOptions`
are exported through `plot-ts/svg` and the root package's `svg` namespace.

## Explicit values, domains and rejection

This profile uses exact observed extrema for both axes, including linear axes.
It does not include zero automatically, pad constants, or choose nice bounds.
For example, line Y `[0.001, 0.0019]` has domain `[0.001, 0.0019]`; the existing
`numeric-axes-v1` line still has its zero-inclusive `[0, 0.002]` domain.

Optional `xDomain` and `yDomain` are exact `[min, max]` pairs. Endpoints must be
finite, ordered and contain every observation relevant to that axis. Equal
endpoints are allowed only when they contain all observations. There is no
extrapolation, silent expansion, clipping or normalized replacement of an
endpoint. Negative zero on a linear axis is represented as zero.

- Every log coordinate and log endpoint must be **strictly positive and finite**.
  Zero, negative zero, negative values, NaN and infinities reject the whole render
- Linear coordinates must also be finite. A linear domain whose subtraction
  `max - min` overflows rejects, including `[-Number.MAX_VALUE, Number.MAX_VALUE]`
- Line series must have exactly the same length as X. All supplied X entries
  contribute to X extent, including those paired only with null Y values
- Only explicit `null` line Y is a missing observation and breaks its path.
  Undefined, array holes and nonfinite values reject; surplus values are never
  silently ignored. All non-null Y values contribute across all series
- Every scatter pair is validated. There is no nonfinite-pair omission on this
  profile. A supplied size remains a finite, nonnegative radius in pixels
- An observed constant has its exact constant domain and one centered tick.
  A truly empty axis defaults to `[0, 1]` linear or `[1, 10]` log. Thus an all-null
  line still uses the supplied X extent and the selected Y fallback
- The full positive binary64 domain, from `Number.MIN_VALUE` to
  `Number.MAX_VALUE`, is supported mathematically on a log axis. Actual rendering
  must still pass guide-label, marker and panel fitting

The new scale/domain fields require `scaled-axes-v1`; using them with an omitted
profile or `numeric-axes-v1` rejects. Other chart families reject the new profile
or its scale/domain fields rather than ignoring them. Explicit undefined means
omission. Unknown scale names/profile versions, null options and malformed
domains reject.

Line `max` is unsupported here; use `yDomain`. Line `area: true`, `smooth: true`
and `labels: true` reject rather than inventing a logarithmic area baseline,
pretending to smooth a straight path, or silently omitting point labels. False
or omitted values are allowed. Existing axis flags must be omitted or true.
Other chart families, signed/symlog axes, arbitrary log bases, axis breaks,
dates, dual axes and secondary-axis conversions remain outside this profile.

## One transform for marks, ticks and grids

For positive `[a, b]`, the normalized position is `ln(v/a) / ln(b/a)`, equivalent
to a base-10 logarithmic mapping. Exact endpoints map to 0 and 1; a constant maps
to 1/2. No independent guide-only log transform or provider-side rescaling exists.
Values `1, 10, 100, 1000` have equal normalized spacing.

Log ticks contain the exact endpoints plus up to three interior powers of ten.
Decimal decades are parsed as complete decimal strings (for example `1e-300`),
never inferred through a runtime logarithm or generated by floating-point
exponentiation. Out-of-range or underflowed candidates are excluded; duplicate
subnormal candidates are not emitted. There are at most 633 exponent candidates.
A fixed bounded selection tries four, two and one intervals, thinning optional
interior decades while keeping both endpoints. Domains entirely within one
decade can show just their endpoints. These are major ticks, without minor ticks.

Linear axes keep the existing bounded numeric tick generator, including zero
when a domain straddles it. Full labels round-trip to their actual tick values.
There is no hidden multiplier, rounded endpoint, unit prefix or false zero.
Horizontal grid lines use the actual selected Y tick positions. X ticks have no
vertical grid lines. Guides expose `data-plot-axes="scaled-axes-v1"` and each axis
adds `data-plot-scale="linear"` or `"log10"`, with its exact domain attributes.

Existing full literal units, escaping, named-series legends, font estimates,
label thinning, exact endpoint retention, marker padding and serialized-box
checks apply. A layout that cannot fit its required guides fails with an
instruction to increase panel size, reduce grid columns/legend rows, or supply
shorter unit wording. Each grid panel owns independent domains.

## Deterministic logarithm and numerical error

The logarithm does not call `Math.log`, `Math.log10`, `Math.log1p` or another
runtime transcendental function. Every input is decomposed into an exact 53-bit
integer binary significand and exponent. Subnormals are first scaled exactly by
2^52. The significand ratio is evaluated with

`ln(m1/m2) = 2 * sum(z^(2k+1)/(2k+1)), z = (m1-m2)/(m1+m2)`.

Here `|z| <= 1/3`. The implementation uses exactly 96 terms, integer fixed point
`Q = 2^256`, and truncation toward zero after each integer division. The same
kernel computes `ln(2)` at `z = 1/3`; the final log ratio is the exponent
difference times that constant plus the significand log. Close ratios, including
adjacent values across exponent boundaries, are combined in fixed point before
rounding. Neither an overflowing raw ratio nor a subtraction of binary64 logs
is performed. No unbounded convergence loop or arbitrary-precision dependency
is used.

A conservative error bound before conversion to binary64 is **less than
2^-230 absolute** over the full positive binary64 range:

1. The analytic tail is bounded by `2*(1/3)^193/(193*(1-1/9))`, less than 1e-94
2. Fixed-point `z` error is less than `1/Q`; square error is less than `2/Q`.
   The contracting power recurrence bounds each term error below `2/Q`;
   truncating its odd-denominator division adds less than `1/Q`
3. Summing 96 terms and multiplying by two is comfortably bounded by `2000/Q`
   for either the significand log or the computed `ln(2)`
4. Binary exponent differences are at most 2097. Both contributions are thus
   bounded by `2000 * 2098 / Q < 2^-230`

The adjacent-input log gap is greater than 2^-54, far larger than twice this
bound. The fixed-point approximations therefore stay ordered for a fixed
positive denominator, including exponent transitions. Converting the fixed
integer to Number, then dividing by the exact power of two, is monotone nearest
binary64 rounding. Adjacent logs can round equal; they cannot reverse order.
Constants and exact endpoints are special-cased before normalized division.

That bound concerns the kernel before its final binary64 rounding. Normalized
division and mapping into a plot introduce their own binary64 rounding. SVG
coordinates then serialize to two decimals, so very close marks can still share
a pixel/coordinate. This is not arbitrary-precision drawing or an all-font,
all-viewer pixel-parity guarantee.

The committed independent reference corpus is generated by Python's standard
library Decimal at 180 digits from exact binary64 values. It covers subnormals,
adjacent values, binary/decimal boundaries, random significands/exponents and
MIN_VALUE→MAX_VALUE. Tests separately check reference error and monotonicity;
a loose error tolerance alone would not detect a small downward boundary jump.
Node 22.22.1 and Node 24.19.0 are the release runtime checks. Pin the runtime,
fonts and native rasterizer for reproducible production reports.

## Surfaces and closed machine-provider boundary

The same native renderer supplies direct calls, `SvgFigure.render()`, HTML,
static frames, reduced-motion frames and independent panels. Lines remain static
during entry motion, as in the existing native API. Scatter retains bounded
entry fade/rise; its guide bands remain static. No line interpolation, animated
scale transition or live-browser playback verification is added.

Existing node-canvas/librsvg rasterization can consume this actual native SVG;
there is no new independent Canvas chart API. The separate browser/ECharts API
and its existing log options are untouched.

Provider V1, V2 and frame input/receipt schemas, complete command objects and
validators remain unchanged and reject this profile and its fields. The native
feature is **not selectable through an existing V1/V2/frame Hub command**. The
separate `render-svg-scaled-v1` command has its own closed contract and requires
explicit provider installation/admission and pin refresh. Bundled native
source and executable identities change; receipts continue binding the actual
source set. An existing execution/raw-describe pin must be deliberately refreshed
to use a rebuilt provider, even though its exposed old capabilities are unchanged.
The build identity is not a claim that a new capability has been admitted.

## Bounded work and observed cost

The new profile validates these per-panel limits **before any logarithm work**:

- At most 65,536 supplied scatter positions
- At most 65,536 line X entries, 256 line series, and 65,536 total supplied Y
  positions summed across those series; explicit nulls count toward the limit

Every line series must still match X length. These limits do not change older
profiles, provider budgets or the number of figure panels. An over-limit panel
rejects the whole render; no partial SVG is returned. Large scatter entry frames
also retain the existing separate motion-target budget, while final/reduced
frames use static rendering.

A successful panel retains at most 131,072 coordinate scalars while resolving
its domains. Log kernels use fixed 256-bit precision and 96 terms; mapping is
linear in supplied positions, with bounded additional guide candidates and
existing bounded guide fitting. There is no hidden memoization, persistent
cache, data normalization, or cross-render reuse. Repeated renders revalidate
current retained arrays and recompute their geometry.

Release measurements use all-unique X and Y coordinates, both axes logarithmic,
for native static line and scatter at 1,000, 10,000, 16,384 and 65,536 positions.
See the [verification report](verification-svg-scaled-axes-2026-10-05.md) for actual
runtime figures. These are local elapsed measurements, not latency promises or a
whole-figure time/memory bound. Figure cost accumulates across panels; very large
SVG output and native rasterization have their own costs.
